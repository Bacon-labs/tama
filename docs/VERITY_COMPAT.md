# Verity Compatibility

Tama v0.1 targets the current Verity smart-contract repository at:

- Repository: `https://github.com/lfglabs-dev/verity.git`
- Commit: `9b0114efcc0af589af63dd3f2eafcdf1a24dbf1e`
- Lean toolchain: `leanprover/lean4:v4.22.0`
- Lake manifest SHA-256: `fa9aef20db5666756527dec5d4a7a1d933041e9728f035bb8f66847d494ed5e3`

The same commit is also reachable from `https://github.com/th0rgal/verity.git`; Tama records the `lfglabs-dev` URL because that is the URL used by the pinned upstream Lake manifest.

## Compatibility Decision

Tama uses Path B from the implementation plan: a Tama-side adapter derives `tama.contract-manifest.v1` from real Verity outputs. Upstream Verity does not currently emit Tama v1 manifests directly.

The upstream compiler interface verified for this commit is:

```sh
lake exe verity-compiler --manifest <module-list> -o artifacts/yul
lake exe verity-compiler --module <Lean.Module.Name> -o artifacts/yul
lake exe verity-compiler --abi-output artifacts/abi -o artifacts/yul
lake exe verity-compiler --trust-report artifacts/trust.json -o artifacts/yul
lake exe verity-compiler --assumption-report artifacts/assumptions.json -o artifacts/yul
lake exe verity-compiler --layout-report artifacts/layout.json -o artifacts/yul
```

`--manifest` in upstream Verity means “read a text file containing Lean module names.” It is not a contract artifact manifest and is not equivalent to Tama’s `tama.contract-manifest.v1`.

## Supported Verity Subset

The v0.1 starter is `ERC20Lite`, not Counter. It must stay inside the proven, compiler-supported subset:

- flat source/spec/proof files generated by Tama aggregate modules;
- `uint256`, `address`, and `bool` ABI types;
- fixed storage and single-key `mapping(address => uint256)` storage;
- ERC20-style `Transfer(address,address,uint256)` event when supported by the pinned compiler path;
- public obligations with fully qualified Lean declarations;
- Foundry mirror tests over generated bytecode.

Counter remains a secondary compatibility fixture for the simplest storage/function path.

## Known Boundaries

Tama must fail closed before producing misleading artifacts for features outside this subset.

- Upstream direct Tama v1 manifest emission is absent; Tama’s adapter is mandatory.
- Raw `rawLog` event emission is compiler-supported, but upstream trust reports classify it as not fully modeled by the current proof interpreters.
- Low-level calls, returndata choreography, runtime introspection, proxy/delegatecall upgradeability, and partially modeled linear-memory mechanics are trust-boundary concerns and must be surfaced by `tama audit`.
- Verity compiler compatibility patches are never applied silently to user projects. Any required patch must be upstreamed, pinned to a Tama-maintained fork, or recorded deterministically in `tama.lock`.

## Verification Commands

These commands are the compatibility baseline for v0.1:

```sh
git clone https://github.com/lfglabs-dev/verity.git
cd verity
git checkout 9b0114efcc0af589af63dd3f2eafcdf1a24dbf1e
cat lean-toolchain
shasum -a 256 lake-manifest.json
lake exe verity-compiler --help
```

Release CI must additionally prove that Tama-generated `ERC20Lite` and the Counter compatibility fixture compile outside the Verity monorepo.
